# AGENTS.md — GeoGallery

AI agent context for GeoGallery, a multi-user personal media gallery and GeoGuessr-like game. It has invite-only OIDC login. Every user has a private library and can share items with other users through albums.

## Context

Media files (photos, videos, 360° content) are stored in MinIO AIStore (S3-compatible) and metadata in PostGIS. A Go backend serves them to a React/Vite frontend. Users sign in through one generic OIDC issuer: Logto Cloud for the hosted instance, Keycloak for dev/E2E. Every media, trip and GPS-track row has an `owner_id`, and every query is scoped to it. The one exception is media reads: a user can also read items that sit in an album they are a member of (`readableMediaCond`). Sharing is by reference, so media rows are never copied and `owner_id` never changes. Media is ingested by browser upload or by the operator command `server scan --user <id>`. The ingest pipeline extracts EXIF, detects 360° content and resolves GPS coordinates; mistakes here corrupt media metadata permanently. IdP setup: `docs/auth.md`.

## API Routes

Auth column:
- **public:** no authentication.
- **user:** a session cookie **or** `Authorization: Bearer gg_pat_…`.
- **session-only:** a session cookie; API tokens get 403.
- **admin:** session-only, and the user must be an admin.

`http.CrossOriginProtection` runs on all of `/api`. A non-owned resource returns 404. Media in an album the caller is a member of is **readable** (list, `/url`, keyframes GET, game), but every media write stays owner-only and returns 404 on shared media. Album routes return 404 to a non-member and 403 to a member attempting an owner-only action. A malformed UUID in an album path → 404; in an album request body (`user_id`, `media_ids`, `trip_id`) → 400. Body checks run before the membership check, so a bad body is 400 even for a non-member. Challenge routes follow the albums: 404 to a caller who does not play in the challenge (a malformed ID too), 403 to a player attempting an owner-only action, and a refused body 400 before either.

## Backend Conventions

- Handler structs hold deps (`*pgxpool.Pool`, `*storage.Client`). Construct with `New*Handler(...)`.
- New routes: register in `newRouter` in `main.go`, inside `r.Route("/api", ...)`. Put them in the right group: the `RequireUser` group by default, or the nested `RequireSession` group for anything irreversible or security-sensitive, with `RequireAdmin` nested inside for admin routes.
- **Owner scoping.** Every handler behind `RequireUser` gets the caller with `auth.MustUser(r.Context())`. It panics if the route is not behind the middleware, and `Recoverer` turns that into a loud 500 instead of an unscoped query.
  - Every SQL read and write filters on the owner, and every insert writes `owner_id`. The exceptions are media reads and album routes, which are scoped by album membership instead (next bullets).
  - A resource the caller does not own returns **404, never 403**. Albums refine this: a non-member gets 404 on everything album-scoped, and a member attempting an owner-only action (rename, delete, manage members, remove someone else's item) gets **403**, because they can see the album. `AlbumHandler.authorize` encodes both.
  - Media **reads** use `readableMediaCond(alias, n)` from `visibility.go`: `(alias.owner_id = $n OR EXISTS (SELECT 1 FROM album_media am JOIN album_members mem ON mem.album_id = am.album_id WHERE am.media_id = alias.id AND mem.user_id = $n))`. It is the single place that encodes read access; never add a second path. The alias is **required** (use `FROM media m` and `"m"`): unqualified, `id`/`owner_id` would resolve to `album_media` columns inside the `EXISTS`. `/api/media` and `/api/game/round` get it through `buildMediaFilter` (`filters.go`), which also builds the shared filters; run `validateMediaFilters` first.
  - Media **writes** keep a literal `owner_id = $n` and never use `readableMediaCond`: location, capture time (set and shift), view settings, keyframes PUT, delete. A member touching a shared item gets 404, and a shift that names one is 404 as a whole, with nothing written.
  - Trips are personal: trip filters (including `unassigned`) are ANDed with `m.owner_id = $1`, and `trip_id` is returned as `NULL` for media the caller does not own.
  - Only an item's owner contributes it to an album, and only while a member: album media inserts select `FROM media m WHERE m.owner_id = $me`, and the composite FKs on `album_media` enforce it in the database.
  - A challenge grants no read access. Its items are drawn from media every player can already read: `challengePoolConds` adds `readableMediaCond` once per player to the Game's own filters, so there is still one place that says who reads what. After that, every query that shows a round, its answer or the guesses on it joins `media` under `readableMediaCond` for the caller (`ChallengeHandler.items`, the guess lookup, `challengeSelect`'s `finished`): a round whose item left the caller's albums is skipped, cannot be guessed, and comes back from the results with `available: false` and nothing else, because the answer and the other players' guesses around it would give its location away. The standings (names, rounds played, scores) are every player's to see. `TestChallenge_NeverShowsMediaThePlayerCannotRead` pins it. One thing a challenge does tell its owner: that a player can read an item (the 409's count, and a drawn round). For a third user's item that can be through an album the owner is not in. Accepted among friends; restricting the pool to albums all players share would close it.
  - Settings are the caller's own: every `/api/me/settings` query and `loadCameraZoneSetting` read or write the `users` row of a literal id, so one user's camera zone never dates another user's file, and one user's video sound never starts another user's videos.
  - Camera clock rules describe one user's cameras. `loadClockRules` and every `/api/camera-clock-rules` query filter on a literal `owner_id`, so one user's rule never dates another user's file of the same model, and a foreign rule ID is 404. `GET /api/cameras` reads only the caller's own media, never `readableMediaCond`: a rule applies to the owner's uploads only.
  - `RunGPSMatcher`, `RunGPSMatcherAround`, `RunTripDetect`, `RunIngestScan` and `RunRetime` take an `ownerID`. Never match one user's media against another user's tracks.
  - Storage counts stay per owner too. The admin's summary (`GET /api/admin/storage`) is the one read across every owner's rows, so it is admin and session only, and it returns each user's totals only, never a trip, album or file name. Each user's own breakdown (`GET /api/me/storage`) filters every query on a literal `owner_id`, never `readableMediaCond`: a shared item counts for its owner, and an album appears only for the caller's own items in it, put there as a member. `TestAdminStorage_Integration` and `TestMyStorage_Integration` pin both. `server backfill-sizes` writes every owner's `size_bytes`, a value only these counts read.
- **GPS stays per owner.** `RunGPSMatcher` (its media query and `bracketingPoints`), `insertExifGPSTrack`, `auto_detect_trips`/`RunTripDetect` and `RunRetime` (its media query, `moveTrackPoint` and the clearing of interpolations) keep their literal `owner_id` filters and must **never** use `readableMediaCond`. Media shared with a user through an album are not that user's rows: their matcher must neither write to them nor read their locations as track points, and their trip detection must never assign them. Comments in `gps_matcher.go`, `trip_detect.go` and `retime.go` say so; `TestSharing_GPSIsolation`, `TestSharing_TripDetectIgnoresSharedMedia`, `TestSharing_NamedTripIgnoresSharedMedia` and `TestSharing_RetimeIgnoresSharedMedia` pin it. So do `RunGPSMatcherAround` and every statement of a capture time change (`applyTimeChange`: its update, `moveTrackPoint`, `moveUnownedTrackPoint`, `createOwnTrackPoints` and the clearing of interpolations), as their comments say; `TestTimeEdit_NeverTouchesAnotherUsersData` and `TestRunGPSMatcherAround_Integration` pin it. `loadTrack` and every query behind the provenance routes keep literal `owner_id` filters too, so an album member gets 404 and no track data (`TestSharing_ProvenanceIsOwnerOnly`). So does every query behind `GET /api/checks` and `GET /api/checks/agreement`: another user's tracks and media shared through an album never enter a result (`TestChecks_IgnoresOtherUsersAndSharedMedia`, `TestChecks_IgnoresAnotherUsersSameLabelAndNearbyPoints` for the residual join, the agreement's samples and gap counts, and `TestChecks_SharedPhotoNeverExplainsAnOrphan`).
- **Auth methods.** `auth.MethodFrom(ctx)` is `MethodSession` (cookie) or `MethodToken` (Bearer `gg_pat_…`). The zero value `MethodNone` never counts as a session. Session-only routes: `GET /api/media/{id}/provenance`, `GET /api/media/{id}/provenance/file`, `GET /api/checks`, `GET /api/checks/agreement`, `DELETE /api/media/{id}`, `DELETE /api/trips/{id}`, `DELETE /api/albums/{id}`, `POST /api/albums/{id}/members`, `DELETE /api/albums/{id}/members/{user_id}`, `GET /api/users`, `POST /api/challenges`, `DELETE /api/challenges/{id}`, `POST /api/challenges/{id}/leave`, `/api/tokens*`, `/api/admin/*`. Granting or revoking album access and listing users' emails need a session, so an API token can never widen who sees the data. Track points, capture evidence and the checks (the owner's track files and findings drawn from their location history) need one too, so no API token can read location history. The camera clock rule routes, `GET /api/cameras` and `/api/me/settings` accept tokens: a rule or the camera zone only changes how the owner's future uploads are dated and the video sound only how their videos start, and neither a rule, the camera list nor a setting is location history. So does `GET /api/me/storage`: it counts the owner's own items per trip and per album, whose names a token reads through `/api/trips` and `/api/albums` anyway. The capture time routes accept them too: like a location set by hand, a time set or shifted is the owner's own correction of their item and can be changed back. Making a challenge names other users as its players, who then see each other's names and scores, and deleting or leaving one drops scores for good, so those three need a session; listing, opening and guessing accept tokens, since a round shows only media the caller reads anyway. `GET /api/albums` takes them with its `member_id` filter too: it says only which of the caller's albums some users are in, which `GET /api/albums/{id}/members` tells a token already. A `Bearer` header is authoritative; other schemes fall through to the cookie.
- **Secrets in logs.** Never log tokens (session, invite, API), ID tokens, query strings or `Authorization` headers. Invite tokens and OIDC `code`/`state` travel in query strings, which is why the request logger (`internal/httplog`) logs `r.URL.Path` only. Tokens are stored as sha256 hashes. Presigned URLs are never logged either, including the one given to `ffprobe`.
- New config values: add to `config.go` with a default that works locally without editing `.env`. `OIDC_ISSUER_URL` is used verbatim; never normalise it.
- **Video tools never detect the input format.** Every `ffprobe` and `ffmpeg` call on an uploaded or stored file passes `-format_whitelist videoDemuxers` (`ingest/video.go`). Left to detect it from the bytes, they treat a DASH manifest under a video extension as a manifest and fetch the URLs and local files it names, on the server. A video in any other container (MPEG-TS, FLV, MPEG-PS or ASF under an accepted extension) is still stored, but ffprobe refuses it: nothing is read from its container (`creation_time`, location tag, 360° detection) and it is never transcoded, so a legacy codec stays unplayable in the browser. A newly accepted container goes into that list too.
- Logging: use `log/slog` (stdlib). `slog.SetDefault` is called in `main.go` — call `slog.Error/Warn/Info/Debug` directly anywhere in the backend. Always log before returning a 500: `slog.Error("context: what failed", "err", err)`. Per-item loops that continue on error must log at Error level, not silently skip.
- Migrations: `000003_description.up.sql` / `.down.sql` — **never edit existing migration files**.
- PostGIS geometry: `GEOGRAPHY(POINT, 4326)`, `ST_MakePoint(lng, lat)` (longitude first!), read back with `ST_Y` (lat) and `ST_X` (lng).
- **EXIF is decoded only through `ingest.ExtractExif` and `ingest.ReadTags`** (`ingest.VideoExif` hands `ExtractExif` the TIFF block it finds in a video), which call `github.com/bep/imagemeta` through `decodeExif` with `LimitNumTags` and `LimitTagSize` set: at its defaults a 60 KB file can cost about 900 MB of allocation. `ExtractExif` then reads the XMP in a pass of its own (`readPano`, `xmp.go`), through the same `decode` and limits, with a `HandleXMP` that tokenises at most 64 KiB and 2,000 tokens of a packet and never fails: imagemeta's own XMP decoder unmarshals a whole packet at once, and a separate pass means a broken or oversized packet costs the projection, never the EXIF. imagemeta reads no XMP from a PNG and only the first XMP segment of a JPEG (no extended XMP). Every tag is read from the one IFD it belongs to (`exifTagsRead`: the Interoperability IFD, which most phones write, reuses the numbers of `GPSLatitudeRef` and `GPSLatitude` and comes first) and with a checked type assertion. Never call imagemeta's `Tags.GetLatLong`, which panics on a reference tag that is not text, outside `Decode`'s recovery. A coordinate of exactly 0 counts as unreadable, because imagemeta reads a rational with a zero denominator as 0. Only the first 1 MiB of a file reaches the decoder (`mediaHeadSize`), so EXIF or XMP stored past that point, possible in PNG, WebP and HEIC, is not read. `registerMedia`, the photo re-read behind `GET /api/media/{id}/provenance/file` and `server retime` decode in one of `exifDecodeSlots` (4 per process, through `inExifDecodeSlot`, by way of `extractExifInSlot` and `videoExifInSlot`; `server scan` and `server retime` are processes of their own), so the total memory and CPU decoding can take in a process follows that number and not the number of uploads or re-reads running; anything else that starts decoding stored or uploaded files takes a slot too.
- **S3 keys** for new uploads: `media/{owner_id}/{32 random hex chars}{.ext}`, built by `newStorageKey`. The extension is lowercased and kept only if supported. Never put the filename or a timestamp in a key: presigned URLs expose the key and would leak game hints. The original name stays in `media.filename`. Older objects keep their legacy `media/{unix_nano}/{filename}` keys. Serve via presigned URLs only (15 min) — the bucket is private; never expose raw MinIO URLs to the frontend. `PresignGet` is the browser's URL, signed for `S3_PUBLIC_ENDPOINT`, a host the backend may not reach (under compose, the host's `localhost`). A URL the backend fetches itself (ffprobe) comes from `PresignGetInternal`, signed for `S3_ENDPOINT`, and never goes to a browser.
- Deduplication: `registerMedia` takes an `io.ReaderAt` (multipart files are spooled, scan opens an `os.File`), computes `file_hash` with `mediaHash` from the head and tail, and looks up `(owner_id, file_hash)` **before** probing, transcoding or uploading: a duplicate returns `registerResult{mediaID: existingID}` (`inserted` false, and no `src` or `zone`: it was dated when first stored) and never touches S3, so upload can still add it to an album. Two concurrent uploads of one file can both miss the lookup; `ON CONFLICT (owner_id, file_hash) DO NOTHING RETURNING id` settles it and the loser's object is deleted again (as is the object of an INSERT that certainly stored nothing; best-effort, logged). Dedup is per owner (no cross-user dedup: the same file from two users is two items); re-uploading or re-scanning the same file is always safe. An empty file is refused.
- **`mediaHash` is frozen.** It is not quite "size + first and last 64 KB": it reproduces what the original streaming code hashed (photos between 128 KB and 1 MB hash only the size and the first 64 KB; probed videos hash only their first 1 MB). Changing it would make every existing row miss its re-upload. `frontend/src/lib/mediaHash.ts` copies it, and both check `frontend/src/lib/mediaHash.vectors.json` (inside `frontend/` because the frontend image is built from that directory alone and `tsc -b` checks tests; regenerate only with `go test ./internal/handlers -run TestMediaHash_Vectors -update-hash-vectors`, which must never change an existing vector).
- Auto-run order after ingest: `RunGPSMatcher` → `RunTripDetect`, for the ingesting owner. Both are called at the end of scan and upload. An upload with `?album_id` then adds the request's new and duplicate media IDs in one `INSERT … SELECT $1, unnest($2::uuid[]), $3 ON CONFLICT DO NOTHING`. If the matcher, trip detection or that insert fails, the request returns 500 and the files stay in the uploader's library without being added to the album.
- After a capture time change: `RunGPSMatcherAround` (every changed item's old and new time: a point at time p only enters the brackets of rows within the match window of p) → `RunTripDetect`, for the owner, once the change is committed, on `context.WithoutCancel` bounded by `timeEditFollowupTimeout` (2 min), so a closed tab cannot stop them half-way. A failure there is logged and answered 200 with `followup_failed: true`, never a 500: the change is committed, and a client retrying a shift would move the items again.
- **Per-owner lock.** `lockOwnerRow` (`owner_lock.go`) locks the caller's `users` row `FOR NO KEY UPDATE`, which does not block the inserts that reference the user, so uploads go on. Camera clock rule POST and PUT take it first (the 100-rule cap; overlapping periods would otherwise deadlock in the exclusion constraint), and so do both capture time routes: each locks its own items, then clears the interpolations near a moved point's old time, which locks further rows in no set order. Trip detection after a concurrent upload does not take it, so a capture time change that Postgres aborts as a deadlock victim (40P01) runs again from `Begin` (`retryOnDeadlock`, 3 attempts in all); nothing is committed before `Commit`, so a retry applies the change once.
- Trip deletion: `DELETE /api/trips/{id}` is only allowed for `user_edited = true` trips. Auto-detected trips are protected; renaming a trip flips it to `user_edited = true`.
- Challenges: a free round and a challenge's round are scored by the same `scoreGuess`, the challenge's on the `max_dist_km` it stored when it was made (a free round takes the client's). A challenge's members are fixed when it is made: the items were drawn for exactly those players, so nobody is added later. The owner always has a `challenge_members` row, inserted in the create transaction, and cannot leave (400); a disabled player keeps their place and score. The items and their answers are drawn and stored in one statement (`challengeDrawSQL`: a `WITH … INSERT … SELECT … LIMIT 5`), so an item deleted meanwhile is simply not drawn, and fewer than five rows roll the challenge back.
- **The challenge draw spreads the rounds; it is not a plain `ORDER BY RANDOM()`.** A random draw follows the number of items, so a place with a thousand photos would fill most challenges. `challengeDrawSQL` orders the pool by three things, each random inside the one before:
  - **Least used first.** An item counts as often as the player who has had it most has had it, in the challenges the new challenge's players play in (`challenge_items` joined to `challenge_members`; nothing else is stored, so a deleted challenge is forgotten, and so is one a player left, for that player). An item is repeated only when the pool has nothing the players have had less often. This is what keeps a place with two photos from coming up in every challenge.
  - **One item per place.** A grid of `challengeDrawGrid` (8) cells a side is laid over the pool's extent, the area the guess map opens on, so it is as fine as the pool is small. Every cell with an item gives one, the cells in random order, whatever the number of items in them; a second item comes from a cell only when every cell has given one.
  - **A random period inside the place.** The pool's time span is cut into `challengeDrawPeriods` (8) equal periods, undated items being a period of their own. A cell's item comes from a random one of its periods, then at random from that period.
  - The positions are dealt at random. A pool at one point or of one instant is one cell or one period (`WIDTH_BUCKET` refuses equal bounds). On a library of 7,730 located items the statement took about 90 ms. `challenge_draw_integration_test.go` pins each rule; a free round is still a plain random item.
- Albums: the album owner always has an `album_members` row, inserted in the create transaction, and it can never be deleted (the owner cannot leave: 400; they delete the album instead). A disabled user keeps their memberships and contributions, drops out of `GET /api/users` and cannot be added again; albums they own stay readable but unmanageable (no ownership transfer).
- Media deletion: `DELETE /api/media/{id}` removes the DB row (cascades to `video_keyframes` and `album_media`) then best-effort deletes the S3 object. S3 failure is logged but does not roll back the DB transaction — the DB is the source of truth.
- **Sizes.** `registerMedia` stores the length it uploads in `media.size_bytes`: the file's own, or a transcoded video's transcode (a transcode it cannot `Stat` fails the file). Rows stored before migration 17 keep `NULL` until `server backfill-sizes` reads their objects' sizes (HEAD). Every count of storage takes `NULL` as unknown, never as 0, and says how many items it leaves out. The storage counts sum the rows, never a bucket listing, so an object no row references (a failed best-effort delete, objects another database such as the E2E one put in a shared bucket) is not counted.
- New handlers should validate UUID path params with `auth.CanonicalUUID` before querying, so a malformed ID returns 404, not a Postgres 22P02 500. The admin, token, album, challenge, camera clock rule and capture time routes already do (and `buildMediaFilter` binds trip and album IDs in canonical form); the other media and trips handlers still pass the raw chi param.

## Frontend Conventions

- All backend calls go through `frontend/src/api/client.ts`. Add a typed helper there, never call `fetch` directly in components. Helpers go through the internal `request()`, which redirects to `/api/auth/login?return_to=…` on 401. `api.me()` opts out and returns `null`.
- The app is wrapped in `AuthGate`. It calls `api.me()`, and renders `LoginScreen` when signed out. Read the current user from `AuthContext`. The Admin tab renders only for `role === "admin"`. This is cosmetic: the backend enforces roles.
- Navigation state lives in the URL (`src/lib/routes.ts`): the tab's path, on Trips and Albums the open gallery and its current item, and on Game the open challenge. A reload or a copied link opens them again, and `LoginScreen` sends the path as `return_to`, so a link survives signing in. There is no router library: `src/lib/history.ts` owns every history entry.
  - `App` takes the tab from the URL at load and on back and forward, and pushes a page entry per tab opened (`pushPage`), so back returns to the previous tab. `/admin` without the admin role, and an unknown path, open the map.
  - A page reads its part of the route when it mounts (`currentRoute()`) and opens the gallery at once, before its list is in. Back or forward onto a gallery's entry while none is open (forward after back) opens it again on the URL's item, from the page's `useHistoryChange` listener. Once the list is in, a trip or album that is not in it closes the gallery with a message; the Albums page also closes an open gallery whose album leaves the list on a refresh. `MediaGalleryOverlay` takes `route` and `initialItemId`: it opens on that item, or on the first one with a notice, and keeps its entry's URL on the current item.
  - A view's URL goes through `useCloseOnBack(onClose, enabled, url)`. The current entry shows the innermost open view's URL, so a view without one (the evidence view, an editor) keeps the gallery's. Changes are written at most every 250 ms: browsers cap history calls, and a held arrow key steps faster.
  - `startHistory` (from `App`'s layout effect, before any page's effects) puts a view from the URL on a view entry above its page's entry, as if opened from the page, so back closes the gallery before it leaves the tab. After a reload the entry is already there; the view takes it over, with the entries of views that were open above the gallery, and closing it pops them all.
  - Back and forward close the views whose entries they leave. Landing on the entry of a closed view, `history.ts` leaves it again unless a view opens for it first and takes it over: the popstate handler runs the views' `onClose` and the `onHistoryChange` listeners inside `flushSync`, so a gallery a page reopens is mounted and waiting before history is brought in line. Without that, React renders after the module has left the entry, and the gallery comes back on a new one, with the URL flashing to the page's on the way. A view without a URL (the evidence view, the Checks view, an editor) is never reopened: its entry is left again at once.
  - The Game page opens the challenge its URL names at once, before its list is in, and again on forward after back (`useHistoryChange`). `ChallengeView` finds out itself whether the caller may see it: a 404 closes it with `CHALLENGE_GONE`, said above the page's list. A challenge's URL names no round: which round is next is the server's to say.
  - Filters, the map's selection and its viewport stay out of the URL. Ticked trips and albums would outgrow the 4 KB login cookie that carries `return_to`.
  - Trip detection gives every trip nobody edited a new ID on each upload, scan or capture time change, so links to those trips break; a renamed or re-dated trip keeps its link.
- Challenges (`components/game/`, `src/lib/challenge.ts`):
  - The Game page's idle screen lists the caller's challenges under Start Round (whose it is, the players, `challengeStatus`, a button that says Play, Continue or Results) and reloads the list whenever a challenge closes. "New challenge…" opens `NewChallengeDialog`, which asks for the players, then for what the items are drawn from, then for a name. The filters are the dialog's own, shown through `FilterFields` (the filter panel's fields): they start from the page's filters at each opening and change nothing on the page. Its albums are only those every ticked player is in, since an album one of them is not in adds only what that player sees some other way. Each change of players asks `GET /api/albums?member_id=…` and cancels the request before it; the albums offered before stay until the answer. A ticked album that leaves the list is unticked and named in one line until it is listed again (`offerAlbums`), and unticking the player never ticks it again; a list left empty says so. With nobody else ticked every album of the caller's is listed, without a request, and so it is when the lookup fails, which is said. The trips are not narrowed: they are the caller's own, and the other players read their items only through albums. The name may be left empty: the dialog then sends the name it shows as the field's placeholder, from `randomChallengeName` ("Cheerful Cheetah"), so the backend's rule for a name stays as it is. Enter among the players and the filters is cancelled (`keepEnterFromSubmitting`), because a browser submits a form on Enter in a checkbox, a radio button or a date field too: only the name field and the button create the challenge. The dialog cannot know whether five items are shared between the players, so a 409's reason, the server's count, is shown as it is; a 404 says a player is gone. The owner deletes a challenge and another player leaves it, each after a `confirm`.
  - `ChallengeView` is a fullscreen view (`z-[1000]`, `useCloseOnBack` with its URL) with the Checks view's keys and focus: `keyBelongsToDialog` first, Tab kept inside, Escape closes except in a text field, the focus moves in and back, and moves to the view whenever the screen changes under the pressed button (Play, Submit, Next round). It loads the challenge, and after every guess loads it again: the round and the results come from the server alone, so a reload of the page resumes on the next round with nothing kept in the browser. Until that reload answers, the score card's button says Continue and the standings' Play button is `aria-disabled`, so the round just guessed is never offered again. A guess is sent once however often Submit is pressed. A 409 (guessed from another tab) or a 404 (the item is gone or no longer shared) returns to the standings with the reason; any other failure keeps the round open, to be sent again.
  - `ChallengeResults` shows one round at a time. A pin says who guessed with the initials inside it, never with its colour: with any number of players, colour only tells the viewer's own guess (the Game's orange, dark text) from everyone else's (blue, white text). The two were checked with the dataviz palette validator against each other and against the map's land and water. `memberInitials` gives every player different initials. The pin is built as an element, never as markup, so nothing from a name is parsed as HTML. The same guesses are listed under the map, best first, with the players who have not guessed yet, so nothing is on the map alone. A round the viewer can no longer read says so and shows neither map nor guesses.
  - A round's thumbnail is a button ("Open round 3's photo full size", 44 px on touch) that opens `RoundItemView` over the challenge (`z-[1100]`): the item in the viewer the round used (`ZoomableImage`; `Panorama360` and `Video360` on the round's 360° view, a `video_360` on its keyframes; a `<video controls>` with `useVideoKeys` and `VideoDecodeNotice`), with nothing of the answer or the guesses over it. A round the viewer can no longer read has no URL and no button. The view has a `useCloseOnBack` entry without a URL, so back closes it alone and the URL stays the challenge's; Escape closes it alone too, since `ChallengeView` ignores every key while it is open. The focus moves in (in a layout effect, before `Video360` takes it for its picture) and goes back to the thumbnail, or to the challenge view when fresh results took the thumbnail away.
  - The URLs come with the challenge and are presigned for 15 minutes. While the challenge on screen is younger than `FRESH_URLS_MS` (10 minutes) the view opens at once on the URL in hand; after that it fetches the challenge again first and says Loading meanwhile. The fresh challenge gives the view and the thumbnails new URLs and the standings as they are now, and the view shows the round at its position, or says why it cannot (`roundItemState`: its item was deleted, is no longer shared, or the results are hidden again because a round became the player's to play). A failed fetch offers Try again; a 404 closes the challenge, as on any load. The thumbnail loads in CORS mode (`crossOrigin="anonymous"`), as the Map card's preview does: the 360° viewers load the same URL as a CORS request, and a no-CORS copy in the browser's cache would fail them. A photo's full-size view loads it in the same mode, so the download is reused.
- Never persist an API token client-side. The plaintext lives only in SettingsPage component state and is cleared when the dialog closes.
- The gallery jumps inside a long trip or album (`components/GalleryJump.tsx`).
  - The "n / N" counter is a field from two items on (plain text in a gallery of one). It empties on focus, showing the number as its placeholder, so typing replaces it without `select()`, which iOS ignores on focus. Enter **or leaving the field** jumps, clamped to 1..N: the iPhone's number pad has no Enter key, and its Done button only leaves the field. Escape leaves it without jumping. The gallery's window listener ignores keys aimed at an input, so its arrows and Escape do nothing while the field has focus.
  - "Go to date" (the calendar button beside it, hidden when no item is dated) opens a dialog with a date field, on the current item's day (the last dated day from an undated item), limited to the days the dated items span. The field shows the day in the format of the browser's language (MM/DD/YYYY in an English (US) browser), as every date field in the app does; a page cannot choose it. It goes to the first item, in the gallery's own order, whose day in the browser's zone (the zone of the times the gallery shows) is that day or later. Undated items never match.
  - An own item's "Why here?" button holds only the date and file name now: a button cannot hold the field. On a portrait phone the label stacks (the jump controls, the date, the file name); on a 360 px phone the calendar wraps onto a row of its own.
- The Trips and Albums pages mark the card whose gallery closed last (a ring and `aria-current`, `src/lib/lastViewed.ts`) and scroll it into view (`block: "nearest"`) once the list has loaded and again each time a gallery over it closes.
  - The ID is remembered in the gallery's `onClose` only, so a link to a trip or album that is not in the list leaves no mark.
  - It is kept in `sessionStorage` under the user's ID: it survives a tab switch and a reload but not the browser tab, and a sign-out in the same tab never shows the next user the album the last one viewed. Every access is in try/catch; without storage the mark lasts until the page unmounts.
  - A trip nobody edited gets a new ID on each upload, scan or capture time change, which drops its mark.
  - It is the only thing the app keeps in browser storage, and `frontend/public/privacy.html` says so. Anything else stored in the browser goes there too.
- Types shared across pages/components live in `frontend/src/types/index.ts`.
- Shared media: the UI decides "is mine" by comparing `MediaItem.owner_id` with the `AuthContext` user. A shared item shows "Shared by {owner_name}" and hides delete, edit location, edit capture time and edit view, and the shift dialog leaves it out. `AlbumMenu` gives an own item add/remove checkboxes and "New album…", and a shared item only a read-only list of the albums it came through (no re-sharing). This is cosmetic too: the backend returns 404 for writes on shared media.
- The evidence view is opened from own items only: the Map card, the gallery's position label, and a Checks finding, whose `media_ids` are the caller's own (a shared item keeps the plain GPS line, and the routes answer 404 anyway). On the evidence surfaces, which are the evidence view, the Checks view and the upload receipts (`src/components/evidence/**`, `src/lib/evidence.ts`, `src/components/checks/**`, `src/lib/checks.ts`, `src/pages/UploadPage.tsx`), times go through `src/lib/time.ts`, and lint forbids `toLocaleString`, `toLocaleTimeString` and `toLocaleDateString` there (tests excepted). Every time names its clock: only the capture time has a camera clock, which comes from the backend and is never derived in the browser. The view takes the focus when it opens, keeps Tab inside and gives the focus back when it closes, because the page behind it is covered but still in the tab order.
- Camera clock rules (Settings → "Camera clocks", `components/settings/CameraClockRules.tsx`): a rule's days are calendar days on the camera's own clock, shown as written and never converted to a zone (`rulePeriod`). Settings and the evidence view name rules and cameras through `src/lib/clockRules.ts`. The rule list, its button labels and the delete confirmation show a rule's make and model as stored, apart (`ruleCameraName`): a rule matches the EXIF `Model` exactly, and `cameraName`, which drops a make the model repeats, would show a typed "Canon" + "EOS R5" (which no Canon file matches) like "Canon" + "Canon EOS R5". The evidence view names a rule that applied, so matched, with `cameraName`. The dialog offers the cameras from `GET /api/cameras` or a typed make and model, and sends `null` for an empty day and always a note. A 400 shows the server's plain-text reason (`ApiError.reason`, which the clock rule helpers fill for a 400 or a 409, and the settings and capture time helpers for a 400 only). A 409 shows the 100-rule cap when its reason is the cap's (`CLOCK_RULE_CAP_REASON`, the backend's `clockRuleCapMessage`), else the overlap sentence, and reloads the list: the list on screen can be behind rules added in another tab or by a script. The section says that items already stored keep their times until the owner edits or shifts them, or an administrator runs `server retime`.
- The Checks view (`components/checks/ChecksView.tsx`) mounts only when the Trips page's "Checks" button is pressed: nothing runs before, there is no badge, and it has no URL (`useCloseOnBack(onClose)`). Its keys and focus follow the evidence view's: `keyBelongsToDialog` first, every key ignored while its `EvidenceView` is open, text fields keep their keys, Escape closes, Tab stays inside, the focus moves in and back. Closing it aborts its requests in flight, and a new run of the checks aborts the one before; a 504 has its own sentence. Findings come first (high severity open, low severity collapsed), then the formats against photos, then the track files: sortable, searchable from `SEARCH_MIN_ITEMS`, 200 rows at a time, rows stacked below `lg`, each time formatted once per row and kept (`formatInstant` costs about 70 µs a call). "Compare files" runs `GET /api/checks/agreement` and keeps asking from `next_from` until it is `null`, merging files by source and saying "Compared N of M files…"; it stops, keeping what it has, on an answer that compares nothing, a failure or a 503 (its own sentence), and "Compare the rest" goes on from there. It adds the "Distance to other formats" (a median distance: bigger is worse) and Spacing columns, whose explanations sit above the table. Refresh and Compare files stay focusable while busy (`aria-disabled`, a click ignored), so the focus never falls to `<body>`. Counts go through `formatCount`, spans that can run to years through `formatSpan`. A finding's Open button, described by its sentence (`aria-describedby`), steps `EvidenceView` through its `media_ids`, wrapping round (no position or stepping for a single item); after a location save, a capture time change or a Re-match there, the checks run again when the evidence view closes, or at once when a Re-match answers after it closed. The evidence view's "Show in trip" (from `item.trip`) replaces it with that trip's `MediaGalleryOverlay`, opened on the item among the photos around it, and closing the gallery brings the evidence view back on the same item. Both change in one commit, so the gallery takes the evidence view's history entry over and gives it back: back closes the gallery first. The gallery stays out of the URL (`inUrl={false}`): the evidence view would keep a URL left on that entry, and a page's back and forward listener would then reopen the gallery under the Checks view. "Show in trip" is a link to `/trips/<id>?item=<id>`, so a Ctrl or Cmd click or a long press opens a tab, and an icon link beside it opens one directly, leaving the Checks view as it is. A location saved, a re-match, a capture time change or a delete in that gallery runs the checks again once the evidence view closes. A time change there that leaves the gallery's trip gone moves the gallery as the Trips page does (below), and with no trip to move to brings the evidence view back on the finding's item and tells it why (`EvidenceView`'s `notice`: `REGROUPED_TRIP_CLOSED` from `src/lib/checks.ts`, then what the gallery said of the change, such as the shift's outcome-unknown notice), so a shift whose answer never came is not repeated unawares. The notice goes when the evidence view steps, closes or opens the trip again.
- Camera time zone (Settings → "Camera time zone", `components/settings/CameraTimeZone.tsx`): the caller's `camera_timezone` from `GET /api/me/settings`, chosen in `CameraZoneSelect` (a native select of `timeZoneNames`, the first option "Server default (…)"), saved with `PATCH` (`null` for the default); Save stays focusable (`aria-disabled`) while there is nothing to save. A 400 shows the server's reason. The Upload page offers the same select for one upload ("Default: your camera zone, …" or the server's), sends a chosen zone as `?camera_timezone` with every batch, and locks it while uploading; the default sends nothing. Both say that a zone applies only where the file gives no offset of its own, and Settings that stored items keep their times until the owner edits or shifts them, or an administrator runs `server retime`, which reads them in the new zone apart from files uploaded with a zone of their own and items whose time was changed by hand.
- Video sound (Settings → "Video sound", `components/settings/VideoSound.tsx`, `src/lib/videoSound.ts`): the caller's `videos_start_muted`, With sound or Muted (radio buttons, the server's default marked "(default)", Save as the camera zone's). Every full-size player starts each video as it says: the gallery, the Map page's view, a Game round, a challenge round's item full size, and `Video360` (the view editor's too). M and the player's own button still turn the sound on and off, and the next video starts as the setting says again.
  - `VideoSoundProvider` loads the setting once the user is signed in. The section reports what it loads and saves (`report`), so a change applies to the next video without a reload, and a first load that answers later never undoes it. Until the setting is known, or when it cannot be loaded, videos start muted (`useVideosStartMuted`): silence bothers nobody, and M gives sound. `e2e/video-keys.e2e.ts` waits for the setting before it starts a round.
  - A player reads the setting once per video, so one that loads or changes while a video is open never touches it: `FullSizeVideo` keeps the value it mounted with (React would otherwise set `muted` over the user's choice), and hosts key it per item; `Video360` reads it as each url starts.
  - A browser refuses sound until the page has had a click or a key (a video opened from a link, after a reload). `Video360` then plays the video muted (`startVideo`, which retries muted on a `NotAllowedError` only), and its bar says Play when even that is refused. A flat video with `autoPlay` waits paused for its play button, as a browser leaves it; a Game round's flat video never autoplays. The Map card's preview and the challenge results' thumbnails stay muted: they are not players.
- Capture times changed by hand (`components/EditTimeModal.tsx`, `components/ShiftTimesDialog.tsx`, `src/lib/timeEdit.ts`), for own items only (the backend answers 404 on shared media anyway):
  - "Edit capture time" sits in the gallery's toolbar (a clock), on the Map page's item card and among the evidence view's actions. The dialog starts from the stored time's wall clock in the browser's zone and sends a wall clock with an IANA zone or a fixed offset; the backend resolves it, and a wall clock the zone skipped comes back as its 400 reason. A stored time in an hour the browser's zone showed twice starts on its own fixed offset, with a hint, because the zone would name the earlier of the two instants. Save stays off while the fields still name the stored time.
  - "Shift times…" sits under the gallery's title (once it holds an own dated item) and on every Trips page card, which loads the trip's items when the dialog opens (`api.listMedia({trip_id})`, aborted when it closes). The dialog groups the caller's own dated items by `camera_model`, items without one by kind; one camera starts ticked, none of several, because a trip often mixes a phone whose clock was right with the camera that was off. Undated items and other people's items are left out with a note.
  - Both are shadcn dialogs with `useCloseOnBack`: `keyBelongsToDialog` keeps the gallery's, the evidence view's, the Map cluster's and the video keys off them, and Escape or the back gesture closes only the dialog.
  - Trip detection after a change gives every trip nobody edited a new ID. ## Media Type Detection

`ingest.DetectMediaType(exifData, ext)`, and for a video ffprobe read `ingest.DetectMediaTypeFromProbe(exifData, ext, probe)`, in `internal/ingest/exif.go`. The extension tells a video from a photo (`IsVideoExt`: `.mp4/.mov/.avi/.mkv/.3gp`); what the file says about its projection makes it 360°:
1. **A video's spherical metadata**: ffprobe's side data `Spherical Mapping` with projection `equirectangular` (`VideoProbeResult.Equirectangular`) → `video_360`.
2. **A photo's XMP**, when it names a projection (`GPano:ProjectionType`, read by `readPano` in `xmp.go` into `ExifData.Pano`). Only an equirectangular image of the whole sphere is 360°. Another projection, such as the `cylindrical` of a Galaxy S20 FE's panoramas, or a part of a sphere (GPano's cropped area smaller than its full panorama, as a photo sphere whose capture was stopped early) is flat, whatever the frame: the 360° viewers wrap the image round the whole sphere.
3. **The frame**, otherwise (`isSphereFrame`): 2:1 within 1% and at least 3000 px wide, from the EXIF dimensions or, for a video, ffprobe's.

The file name is never read. Until #28 its keywords (`360`, `pano`, `panorama`, `spherical`) came first: on one real library they made 28 flat photos and 1 flat video 360° and found no 360° item the other rules missed, since "360" turns up in dates and counters (`…_143602.jpg`, `P1036012.JPG`) and a phone's `PANO` is a flat panorama. Insta360's own patterns are left out too: a reframed export keeps the name of the 360° clip it was cut from (5 flat videos there), Insta360 also makes flat cameras, and its make, `Arashi Vision`, was on no 360° photo the frame missed. On that library all 126 360° photos had a 2:1 frame and 122 the GPano XMP too, and all 275 360° videos had the spherical metadata.

New ingests only: stored items keep their type, which the owner will correct with #27.

## `taken_at` Fallback Priority

Both ingest paths follow the same order:
1. EXIF `DateTimeOriginal` (IFD0 `DateTime` only when that tag is missing), read by `ingest.ExtractExif(r, cameraZone)`. For a video, the EXIF the camera keeps inside the file, only when its make's camera rule sets `video_time_from_exif` (`ingest.VideoExif`)
2. The video container's `creation_time` (ffprobe, UTC)
3. The date and time in the file name (`ingest.FilenameTime`), read in the camera zone (below)
4. File modification time (scan: `DirEntry.Info().ModTime()`; upload: `file_mtime` form field in ms-since-epoch sent by the browser)

`registerMedia` gathers them in a `captureReading`, whose `takenAt` takes them in this order and `captureSource` names the one that won.

**The EXIF time is a wall clock without a zone.** `takenAt` in `exif.go` picks the offset and never uses the server's own zone:
- The photo's GPS clock: `GPSDateStamp` + `GPSTimeStamp` (UTC). It is used when wall minus GPS lands within `gpsClockTolerance` (2 min) of a real UTC offset (whole hours, or the fractional offsets in `fractionalOffsets`). A stale fix (minutes or days old, 1970-01-01) falls through.
- Otherwise the owner's camera clock rule: a row of `camera_clock_rules`, defined by the owner in Settings, saying which UTC offset one of their cameras showed during a period. `ingest.ClockRules.Match` takes the rule whose make and model equal the file's EXIF `Make` and `Model` (after `CleanTag`, without case) and whose days hold the wall clock's date. The days are on the camera's own clock, both included, `NULL` for an open end, and are matched against the wall clock, never UTC, because the rule is what turns that clock into UTC. A file without a `Model` matches no rule. The rule outranks `OffsetTimeOriginal` and the camera zone because it is what the owner knows about that camera and its files do not say: the owner's DC-TZ200 shows UTC+2 all year and writes `+01:00`, so its winter photos came in an hour late. The GPS clock outranks the rule because it is measured.
- Otherwise `OffsetTimeOriginal`, trusted unless the make's camera rule sets `ignore_offset_tag`. It follows a phone abroad, and many phones (the Galaxy S24 on every photo) write no GPS timestamp. Panasonic's rule ignores it. A Panasonic writes the offset of its zone setting, and on one real library a DC-TZ200 wrote `+01:00` all year while its clock, set forward by hand, showed summer time. The value alone cannot separate it from a phone in London, so the exemption goes by make. An offset that is blank or not in real use (`isRealOffset`) falls through.
- Otherwise the camera zone (`MediaRegistrar.cameraZone`; nil reads UTC), with that zone's DST on that date: the zone the upload (`?camera_timezone`) or scan (`--tz`) named, else the owner's setting (`users.camera_timezone`, Settings → "Camera time zone"), else `CAMERA_TIMEZONE`. Only this last fallback is per user or per upload; the GPS clock, the clock rule and the offset tag still win. `ingestCameraZone` chooses it once per request or scan, before the body is read, so every file of it, and its receipt, use the same zone; a stored setting the server can no longer load fails the request or scan. `capture_evidence.camera_zone_from` records who named it (`batch`, `user`, `server`).

`ExifData.TakenAtZone` says which one applied (`ingest.ZoneGPS`, `ingest.ZoneClockRule`, `ingest.ZoneOffset`, `ingest.ZoneCamera`), and `ExifData.ClockRule` holds a copy of the clock rule when one applied.

**The file name's time is a wall clock too, read only in the camera zone.** Phones and apps name a file by when it was taken, and an edited copy whose EXIF was stripped keeps the name while its file time becomes the day it was copied. `ingest.FilenameTime` (`ingest/filename.go`) reads a date and a time with seconds where a run of digits starts and ends: `20230729_210400`, `IMG_`/`VID_`/`PANO_20230729_210400`, `2012-08-24_18-14-24_124` (Motorola; the milliseconds are not read), `2023-07-29-21-04-00` (screenshots), `2012-08-24 18.14.24` (Dropbox), `WP_20140712_12_34_56_Pro`. The date's two separators must be the same (none, `-`, `_` or `.`), and so must the time's; the date and the time are apart (`_`, `-`, a space or `T`), so fourteen digits in a row (`IMG20230729210400`) are not read. It must be a real date and time of day in the years 1990–2099. A digit right before or after, as in a Unix time in milliseconds or a Pixel's `PXL_20230729_210400123` (whose time is UTC), means no time, and so do two different dates and times in one name. A date alone (WhatsApp's `IMG-20230729-WA0001`) gives none. Only the last path element is read. The wall clock is read in the camera zone with its DST on that date, as an EXIF time without an offset; the owner's clock rules never apply, since a name says nothing of the camera. `capture_evidence` records `src: "filename"`, `zone: "camera"` and the offset used. Never use imagemeta's `Tags.GetDateTime`, which applies its own zone rules. Before `CAMERA_TIMEZONE`, a Docker server read every EXIF time as UTC.

**Camera rules live in `backend/camera-rules.json`, never in code.** `CAMERA_RULES_FILE` names the file. Each rule names a make (matched without case or surrounding space), sets `ignore_offset_tag`, `video_time_from_exif` or both, and says `why`. `config.Load` refuses a missing file, an unknown key, a rule without a make or a `why`, a rule that changes nothing, and a second rule for one make, so a misspelt rule stops the backend instead of silently not applying. The rules travel in `ingest.CameraZone.Rules` to ingest, the file re-read and `server retime`. They say what a make writes, for every user. What one user's camera showed during a period is that user's camera clock rule, in the database, never an entry here.

**Camera clock rules are per user.** They reach `ExtractExif` and `VideoExif` in `CameraZone.Clock`, so a Panasonic video dated from its `PANA` EXIF gets the rule for the model that EXIF names. A clock rule never makes a video dated from its EXIF by itself; that stays the make's `video_time_from_exif`. `registerMedia` loads the owner's rules (`loadClockRules`) once per file, before its EXIF is decoded, duplicates included, and never uses the registrar's own `cameraZone.Clock`. The file re-read loads them the same way after the item lookup, and `server retime` once per run. A failed load fails the file (upload and scan count it as failed), makes the re-read answer 500 and stops retime before it reads anything: read without the rules, a file would get a time its owner has said is wrong, and a later upload of it would be skipped as a duplicate.

A camera clock that was simply wrong for a while, such as one left on summer time through a winter, cannot be told from its files: a Panasonic's maker-note `TimeStamp` (0x00af) is its own idea of UTC, `DateTimeOriginal` minus its offset, on public samples and on one real library. Its owner says so with a camera clock rule. A clock that was off by something other than a quarter-hour offset, or wrong on single items, is corrected by its owner instead: a shift of the items it dated, or a time set by hand on one item ("Times changed by hand" below).

`ExtractExif` keeps what it read before a decode error: an old Motorola writes a broken tag after its model and position. Old Sony cameras write a zero-length tag in the Exif IFD, which costs nothing, and their other tags are read. A file with no readable EXIF falls through to the next source.

Whatever the source, a time whose UTC year falls outside 1–9998 is dropped and `taken_at` stays `NULL`; the next source is not tried, and `capture_evidence` names no source for it. `time.Time` marshals only the years 0–9999, and one year is kept in reserve at each end because pgx returns a time in the server's zone.

**The derivation is recorded.** Since migration 10, `registerMedia` writes `media.capture_evidence` on every new row: what produced `taken_at` (`src`), which zone rule applied, the wall clock, offset tag and GPS stamp as written, the container and file times even when another source won, the date and time the file name holds (`name_wall`, `YYYY-MM-DD HH:MM:SS`, likewise), and the camera zone in effect (shape: `docs/gps-debugging.md`). Text from a file goes through `ingest.CleanTag` and a value that cannot be parsed is null, so this can never fail an upload. Older rows stay `NULL`: the evidence view re-reads their file on request and says it used today's rules. Neither path moves `taken_at`. Since the clock rules, the evidence also has `clock_rule`, a copy of the owner's rule (`{id, make, model, offset_min, starts_on, ends_on}`) exactly when `zone` is `clock_rule`, because the rule may later change or go, and `retimed_from`, null from ingest. Rows recorded before then lack both keys. Since per-user zones it also has `camera_zone_from`, missing from rows recorded before them (which were read in the server's zone). Since names are read it also has `name_wall`, missing from rows recorded before then.

A change to a rule of either kind, a deleted clock rule included, applies to new ingests only; stored rows keep their times until an operator runs `server retime --user <id> [--apply]` (`RunRetime`). There is no button for it; a user can instead set or shift their own stored times by hand ("Times changed by hand" below), which retime then leaves alone.
- It reads with the camera rules, the user's clock rules and the user's camera zone setting (else `CAMERA_TIMEZONE`), loaded once. An item whose `capture_evidence` says its upload or scan named a zone (`camera_zone_from` `batch`) is read in that recorded zone instead (`storedItemCameraZone`): a zone stated for some files stays with them, while the rest follow the user's zone today. The file re-read behind `GET /api/media/{id}/provenance/file` chooses the same way. Any existing user is accepted, disabled or unclaimed too, since it is a repair.
- A photo (`photo`, `photo_360`) is read from the same 1 MiB head ingest read (`storage.ReadHead`), through `ExtractExif`. A video is read only when a camera rule sets `video_time_from_exif`, from the same head, through `VideoExif`; otherwise nothing is fetched for it. Never ffprobe. Both decode in an EXIF decode slot.
- It changes only rows whose stored `taken_at` is that EXIF wall clock at some quarter-hour offset of at most 14 h (`sameWallClock`), within `retimeTolerance` (5 s: a Panasonic MP4's container time sits a second off the wall clock in its EXIF). A row within 5 s of the new time counts as `unchanged`, one with no EXIF time (and no name time it may take, next bullet) as `not_exif`, and any other as `mismatched`, which is logged and left alone.
- A file without an EXIF time takes the date and time its name holds, in the item's camera zone, when its stored time came from the name or from the file time, which ingest now ranks below the name (`nameMayDate`): its evidence says `src` `filename` and the stored time is the name's wall clock at some offset (a new camera zone), or `src` `mtime` and the stored time is the recorded `file_mtime` (`cameFromNameOrFileTime`); any other stored time is `mismatched`. A row without evidence (ingested before migration 10) qualifies only as a photo, which without an EXIF time could only be dated by its file time; a video may have been dated by its container, which outranks the name and which retime never probes, so it stays `not_exif`. No video object is read for this.
- A row whose owner set or shifted its time (`time_edit` not NULL) is counted as `edited` and skipped before its object is read, even when its time is the EXIF wall clock at another offset. The row lock below also requires `time_edit IS NULL`, so an edit made after the listing makes that row fail, even one that left `taken_at` where it was listed; a re-run counts it as edited.
- Per change, in one transaction that first locks the row while `taken_at` still holds the old value, it:
  - clears an interpolated location;
  - moves the item's `exif` point (if the EXIF has a position) and `manual` point (if `gps_source = 'manual'`), writing the item's own position at the new time (`moveTrackPoint`). Nothing is created where no point existed. The old point stays while another item that would have made it is still at that second, and is then given that item's position: for an `exif` point a photo located from its EXIF (never a video located from its tag, which makes no point, nor an item placed by hand, which has its own `manual` point), for a `manual` point any item placed by hand (`trackPointOwnersSQL`);
  - when a point moved, clears interpolated locations within the match window of its old time, videos included;
  - rewrites `capture_evidence` (`retimedEvidence`): the EXIF and name keys (`src`, `zone`, `wall`, `gps_utc`, `wall_minus_gps_s`, `offset_tag`, `offset_ignored`, `offset_used_min`, `camera_zone`, `camera_zone_from`, `camera_zone_utc_fallback`, `make`, `model`, `exif_partial`, `clock_rule`, `name_wall`) come from the re-read, `by` becomes `retime`, and `retimed_from` holds the old `taken_at` in RFC 3339 UTC. The container and file keys keep what ingest recorded, and are null on a row that had no evidence. A missing `camera_model` is filled from the EXIF.
- It then runs `RunGPSMatcher` (interpolated rows included) and `RunTripDetect` for the owner on every `--apply`, even with nothing to change, so a re-run finishes an interrupted one.
- A matcher run of the owner's that overlaps it (an upload, a track import, a manual location, a capture time change, Re-match) writes a position only to a row whose `taken_at` and `gps_source` are still as it listed them, so it never puts a position from the old time on a retimed row or over a location set by hand meanwhile. It can still place a neighbour from a point's old time, if it read the point before retime moved it and writes after retime cleared the neighbour; a later run keeps that position when nothing else brackets the item. A capture time change also moves track points and clears interpolations in a transaction that retime's per-row transaction (which takes no owner lock) can deadlock with; a retime row that loses is counted as failed. Run `--apply` while the user is not uploading, importing tracks, re-matching or changing capture times.
- A `taken_at` corrected by hand with SQL is undone by the next `--apply` when it is the EXIF wall clock at another offset; one set or shifted through the capture time routes has a `time_edit` and stays. A camera whose clock showed a wrong offset needs a clock rule all the same: a shift corrects the items already stored, and only the rule dates its later uploads.
- stdout has one line per change, in `taken_at` order, both times in UTC: `2019-03-13T18:28:15Z -> 2019-03-13T17:28:15Z  -1h0m0s  clock_rule(Panasonic DC-TZ200 UTC+02:00)  interpolated  <id>  P1033627.JPG`. That is the shift, the zone (with a clock rule's camera and offset; `filename` for a time from the name), the `gps_source` before the change (`-` without a location), the ID and the file name, last and quoted when it holds a control character. Then the counts, and on a dry run `dry run: nothing written; re-run with --apply`.

**Times changed by hand.** The owner sets one item's time (`PATCH /api/media/{id}/taken-at`: a wall clock read in an IANA zone, with that zone's DST on that date, or at a fixed offset) or moves several by one amount (`POST /api/media/shift-time`), from the gallery, the Map card, the evidence view and the Trips page's cards.
- `capture_evidence` is never touched: it keeps saying how the file's time was read. The change is recorded in `media.time_edit` (migration 14, `timeEdit` in `media_time.go`), every key always present: `{v, kind, at, from, original, delta_s, wall, zone, offset_min}`. `kind` is `set` or `shift`, `at` when the change was made (server clock), `from` the `taken_at` before it (null for an undated item), `original` the `taken_at` before the first change through these routes (carried over from the stored record, so null when the first change dated an undated item), `delta_s` the new time minus `from` in seconds (null when `from` is). A set also keeps the wall clock as entered, the zone named (null for a fixed offset) and the UTC offset it was read at in whole minutes; a shift has null there. Each later change rewrites the record and keeps `original`. NULL means the time was never changed this way. The record reaches only the owner's provenance (`time.edit`), never `/api/media` or the Game.
- A time changed by hand outranks every reading of the file: `server retime` leaves the row alone (above), and only another set or shift moves it.
- Per item, in the change's transaction (`applyTimeChange`), as retime does: `taken_at` and `time_edit` are written and an interpolated location is cleared. The item's own points move with it (`moveTrackPoint`): the `exif` point of a photo located from its EXIF, and the `manual` point of an item placed by hand. A photo placed by hand also takes along the `exif` point ingest made at its old second, with that point's own position, since its EXIF position is on no row (`moveUnownedTrackPoint`): only while no other of the owner's photos located from its EXIF or placed by hand sits at that second (`otherPhotoAtSQL`: any of them may have made it; an unlocated or interpolated photo cannot have), and yielding to a point already at the new second. One case is accepted: a photo placed by hand that never had an EXIF position carries along a point a since deleted photo left at its second. An item that had no time gets its points at the new time, as ingest or a manual location would have made them (an existing point at that second is kept). When a point moved, the interpolations within the match window of its old time are cleared.
- A shift moves its items one by one, latest first for a shift later and earliest first for one earlier, so two items an hour apart shifted by an hour never meet at one second and each point keeps its own item's position.
- After the commit the matcher runs around every old and new time and trip detection follows (Backend Conventions). A matcher run that overlaps a change writes only to a row whose `taken_at` and `gps_source` are still as it listed them, as with retime.

The existing deployments were repaired once with `server retime` and `server video-locations` from commit `f2afa0d` (branch `fix/exif-offset-video-location`). `retime` has since been ported into `main` as above. `video-locations` is still not in `main`: port it from that commit if a later change needs that repair again.

For a video, `taken_at` is the container's `creation_time`, unless its make's rule sets `video_time_from_exif`. On Samsung phones that is when the recording ended (about 2 s after start + duration), so it sits later than the time in the filename. Insta360 files do not behave this way, so it is not corrected.

A Panasonic MP4's `creation_time` is the camera's wall clock marked UTC, so its videos came in late by the camera's offset (2 h in summer). Its EXIF, with the same wall clock (the recording's start) and the offset tag, sits in the `PANA` box in `moov/udta`, framed as `FF D8 FF E1`, the APP1 length, `Exif\0\0`, then the TIFF block, at offset 0x10, 0x4068 or 0x4080 of the box's payload (ExifTool's offsets; the GH6 uses 0x200080, out of reach). `ingest.VideoExif` finds it in the first 1 MiB, which holds it because Panasonic writes `moov` first, and reads it like a photo's, with the owner's clock rules, in an EXIF decode slot. No position and no size come from it. It is read after the hash, so `probeVideo` and `file_hash` stay what they were, and its model fills `camera_model`. A transcode drops the `PANA` box, so `TranscodeH264` gets the time ingest stores as the new container's `creation_time`.


## Video location tag

`ingest.parseProbeOutput` reads a video's position from the container's `location`, `location-eng` or `com.apple.quicktime.location.ISO6709` tag: ISO 6709 in decimal degrees. The degrees-and-minutes forms and `+00.0000+000.0000/` (no fix) are refused. `registerMedia` stores it with `gps_source = 'exif'`, which covers everything read from the file itself. It makes **no track point**: the tag can be the phone's last known fix and `taken_at` is the end of the recording, so the pair is too loose to place other media.

Known limit: a video keeps its tag even when a dense GPS log covers the clip, because the matcher leaves `exif` rows alone. On a real library, tags from 2022 on agreed with such a log to within 20 m; 4 of 16 tags from 2017 were 400 m to 4 km off it.

- **Composite trip FK:** `media (trip_id, owner_id) → trips (id, owner_id) ON DELETE SET NULL (trip_id)`. The database itself makes it impossible for media to sit in another owner's trip.
- **Album FKs (migration 9):** `media_id_owner_key UNIQUE (id, owner_id)` on `media` backs two composite FKs on `album_media`:
  - `(album_id, owner_id) → album_members (album_id, user_id) ON DELETE CASCADE`: only members contribute, and leaving or removal takes that member's contributions with them.
  - `(media_id, owner_id) → media (id, owner_id) ON DELETE CASCADE`: only the media owner can contribute an item (no re-sharing), and deleting the media removes it from every album.
  - Deleting an album cascades its members and contributions; the media rows are never touched.
- **Challenge FKs (migration 15):** `challenge_scores (challenge_id, position) → challenge_items ON DELETE CASCADE` and `(challenge_id, user_id) → challenge_members ON DELETE CASCADE`. Only a player guesses, and only a round that exists; the primary key makes the guess the only one.
  - Deleting a media row takes its round and the guesses on it out of every challenge; the other rounds keep their `position`, so positions can have gaps.
  - A player who leaves takes their guesses along; deleting a challenge cascades players, rounds and guesses. The media rows are never touched.
  - A challenge row gives no read access: `readableMediaCond` knows nothing of these tables.
- **Trip detection** is the SQL function `auto_detect_trips(p_owner UUID, gap_hours INT)`. It deletes and rebuilds that owner's auto trips; named (`user_edited`) trips keep their media and their dates. Since migration 12, an item with no trip whose day falls within a named trip's `start_date`–`end_date` first joins that trip, as a date edit of the trip would have put it there; only the rest are grouped by `TRIP_GAP_HOURS`, so the auto trips on either side of a named trip stay apart. The day is `taken_at::date` in the session's zone (UTC under compose), as in `PATCH /api/trips/{id}`. A trip without both dates takes nothing. Where named trips overlap, the narrowest wins, then the latest start, then the lowest id.
- Users are never deleted, only disabled (`ON DELETE RESTRICT` on owned data).
- GPS resolution priority: EXIF (for a video, its container's location tag) → timestamp-interpolated from the owner's `gps_tracks` → null. Never from another user's tracks or shared media.

## Key Design Decisions

- **Invite-only multi-user with one generic OIDC issuer.** No vendor SDK in Go or React. Social login (Google, Facebook, …) is configured in the IdP. Users are keyed by (configured issuer, `sub`), so adding issuers later would not break the schema. An unknown identity without a valid invite is rejected, and the first admin comes from `server invite --admin`, never from "first login wins".
- **Logto Cloud for the hosted instance; Keycloak as the dev/E2E IdP** and the documented self-host option. The code paths are identical. Supabase Auth and Hanko are not supported (see `docs/auth.md`).
- **Backend-for-frontend sessions.** Same-origin `/api/auth/*` routes. Opaque server-side sessions in an HttpOnly, SameSite=Lax cookie, stored hashed, with a 30-day absolute TTL. Logout and disabling a user take effect immediately, and there is no signing secret to manage. No CORS; `http.CrossOriginProtection` guards state-changing (non-GET/HEAD/OPTIONS) requests.
- **Personal API tokens** (`gg_pat_…`, sha256-hashed, always expiring, ≤ 365 days) for scripts. They cannot delete media, trips or albums, manage tokens or album members, list users, read provenance or the checks, make, delete or leave a challenge, or reach admin routes. They can play one: a round shows only media the caller reads anyway. They can create, change and delete the owner's camera clock rules, which only change how future uploads are dated, and set or shift the owner's capture times, which, like a location set by hand, are the owner's own correction and can be changed back.
- **Ownership in the schema.** `owner_id NOT NULL` on media, trips and gps_tracks, a composite trip FK, and per-owner dedup. Non-owned resources return 404. `readableMediaCond` is the single place that encodes media read access.
- **Sharing through albums only, by reference.** No per-media grants: to share one photo, put it in an album. Owner + members; every member views everything and adds or removes their own media, and only the owner renames, manages members, deletes the album or removes other people's items. No re-sharing: only an item's owner puts it into an album, and only while a member. Contributions leave with the member: composite FKs tie each contribution to the media owner and to a membership, so leaving or removal takes that member's items out of the album. Trips and GPS stay personal. A share exposes the item's location, `gps_confidence`, `gps_source`, `taken_at`, `filename` and its EXIF, which is intended. Design: `docs/sharing-albums.md`.
- **A challenge draws from what every player already reads, and keeps its own answer.** A challenge is five items fixed when it is made, one scored guess per player and round (the primary key of `challenge_scores`), and a table of the totals. It grants nothing: the items come from the Game's filtered set narrowed to what every player can read, and a round is shown, guessable and listed in the results only while `readableMediaCond` still holds for that player, so leaving an album also closes its rounds. The answer (location, capture time, confidence) and the scale (`max_dist_km`, the guess map's bounds) are copied when the challenge is made: every player is scored against the same answer on the same scale, whatever the item's owner corrects later and whatever a client sends. The players are fixed for the same reason the items are. The five items are spread over the pool, not sampled from it: one per grid cell of the pool's extent and a random period inside the cell, taking first what the players have had least, so neither the place with the most photos nor the place with two fills the challenges. What the players have had is read from the challenges themselves, so nothing more is stored about anyone. Which round is next is decided by the server on every request, so nothing about a game in progress lives in the browser. Players can find the items on their own map; that is accepted among friends.
- **Folder ingest is an operator CLI** (`server scan --user`), not an HTTP endpoint: it needs server filesystem access.
- **Opaque S3 keys and a private bucket.** Presigned URLs reveal neither the filename nor the upload time. EXIF inside served files is an accepted game-hint risk.
- **MinIO AIStore over standard MinIO** — AIStore edition for performance; requires a license file.
- **golang-migrate over Atlas/goose** — plain SQL files, no DSL, easy to read in git history.
- **Leaflet/OSM over Google Maps** — no API key required, fully offline-capable.
- **chi over Gin/Echo** — handlers are plain `http.Handler`, zero lock-in, composes with stdlib middleware.
- **File mtime as upload fallback** — EXIF `DateTime` preferred; browser sends `file_mtime` (ms-since-epoch) so the server can use real file mtime instead of `time.Now()`.
- **Capture times in a configured camera zone, not the server's.** EXIF times have no reliable zone. The camera zone (an upload's or scan's own, else the owner's setting, else `CAMERA_TIMEZONE`) decides unless the photo's own GPS clock, the owner's camera clock rule or `OffsetTimeOriginal` gives the offset. The offset is trusted by default, because a phone's is right even abroad, and exempt by make in `backend/camera-rules.json`, because a camera whose clock was set forward by hand writes the offset of its zone setting. Camera-specific rules are data, not code. On a real library, the GPS clock agreed with the camera zone on every accepted reading, the 2-minute tolerance rejected every stale fix, and all Samsung offsets were right.
- **Make-wide camera rules in a file, one user's camera clock in the database.** `backend/camera-rules.json` holds what a make writes, for every user (an offset tag to ignore, videos dated from their EXIF), and the operator changes it with a deploy. A clock that one camera showed during a period (the owner's DC-TZ200 on summer time all year, an Insta360 ONE RS on UTC+1 through summer 2022) is a fact about one user's camera, so it is that user's row in `camera_clock_rules`, defined by the user in Settings, and it never applies to another user's file of the same model. The GPS clock outranks a rule, because it is measured; a rule outranks `OffsetTimeOriginal` and the camera zone, which are what the camera got wrong. A rule dates new ingests only. Stored rows move through the operator command `server retime`, which records that it ran (`by: "retime"`, `retimed_from`), so a repaired row can be told from an untouched one. The user corrects their own stored times by hand instead.
- **Hand corrections are recorded apart and outrank every rule.** A capture time the owner set or shifted is recorded in `media.time_edit`, not in `capture_evidence`, which keeps saying how the file's time was read; the evidence view shows both. `time_edit` keeps the time before the change and before the first one, so a correction can be set back by hand. `server retime` never reads or moves an edited row: the owner's own statement outranks any reading of the file, even one that is the EXIF wall clock at another offset. A follow-up failure after the commit is a 200 with `followup_failed`, never a 500, because a client retrying a shift would move the items twice.
- **Partial hash dedup** — the size plus (roughly) the first and last 64 KB are hashed, so dedup never reads the full file; see `mediaHash` for the exact, frozen definition. The browser computes the same hash and asks `POST /api/media/known-hashes` first, so a re-upload sends only new files; the server still hashes everything it receives, so a wrong browser hash costs only bandwidth.
- **Cursor pages for the media list.** `GET /api/media` names the next page by the position of the last item listed (`X-Next-Cursor`), never by an offset: an item added or deleted meanwhile moves no item across a page boundary, and a page costs the same at any depth. Dated and undated items are queried apart, so Postgres walks `media_taken_at_idx` back from the cursor and stops after a page. On 350k synthetic rows a page of 5,000 took about 50 ms at any depth, where an OFFSET page took about 500 ms, and generic plans of the cached statements matched. `readableMediaCond` stays one condition: Postgres runs its `EXISTS` as one hashed subplan per query, so the own ∪ shared `UNION ALL` of #36 was not needed. A user who owns a small share of a large instance still walks most of the index per page (90–160 ms there, against 230 ms with OFFSET); that is where the split would help.
- **Storage use from the rows; the admin sees totals, each owner their own breakdown.** `media.size_bytes` is written at ingest and filled once by `server backfill-sizes` for older rows, so storage use is plain aggregates over the rows, never a bucket listing: it counts what items reference, and an orphaned object is not counted. A size never known stays `NULL` and counts as unknown, never as 0. The admin's summary gives each user's totals (items, size, track points) and nothing inside a library: trip and album names are the owner's and their album members'. Each user sees their own items per trip and per album in Settings; albums hold references, so an item counts in each album it is in. The admin's summary runs only when asked, because counting the track points reads the whole `gps_tracks` table.
- **Relative scoring** — game location score is relative to the geographic spread of the media collection (`max_dist_km` from `NewRound`), not a fixed global scale; GPS confidence adjusts tolerance. With `owner` unset the spread includes shared media, so a friend's far-away album changes the scale; `owner=mine` restores own-only scoring.
